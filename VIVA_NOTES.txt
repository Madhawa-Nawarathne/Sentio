--------------------------------------------------------------------------------
GATE 1: Backend Auth Middleware (MAIN SECURITY GATE)
--------------------------------------------------------------------------------
LOCATION: backend/routes/authMiddleware.js

SIMPLE MEANING:
  Like a security guard at the door.
  Checks if the request has a valid JWT token.
  If YES  -> let the user in (call next())
  If NO   -> block with 401 Unauthorized

CODE:
------------------------------------------------------------
const jwt = require('jsonwebtoken');

const authMiddleware = (req, res, next) => {
  const authHeader = req.headers['authorization'];
  if (!authHeader) {
    return res.status(401).json({ message: 'No authorization header, access denied' });
  }

  const token = authHeader.split(' ')[1];   // "Bearer TOKEN" -> take TOKEN
  if (!token) {
    return res.status(401).json({ message: 'No token provided, authorization denied' });
  }

  try {
    const decoded = jwt.verify(token, process.env.JWT_SECRET || 'your_jwt_secret_key_here');
    req.user = decoded;   // save user id & username on request
    next();               // allow access
  } catch (err) {
    res.status(401).json({ message: 'Token is not valid' });
  }
};

module.exports = authMiddleware;
------------------------------------------------------------

WHERE IT IS USED (routes that need login):
  - backend/routes/auth.js      -> /me , /change-password
  - backend/routes/posts.js     -> get feed, create, like, delete
  - backend/routes/comments.js  -> create comment
  - backend/routes/users.js     -> almost all user routes

HOW TO EXPLAIN IN VIVA:
  "authMiddleware is our backend gate. Every private API route uses it.
   It reads the JWT from the Authorization header, verifies it, and
   attaches the user info to req.user so the route knows who is logged in."

GATE 2: Frontend ProtectedRoute (PAGE GATE)
--------------------------------------------------------------------------------
LOCATION: frontend/src/App.jsx

SIMPLE MEANING:
  Blocks pages like Feed, Profile, Settings if user is NOT logged in.

const ProtectedRoute = ({ children }) => {
  const { isAuthenticated, loading } = useAuth();

  if (loading) {
    return <div>Loading SENTIO...</div>;
  }

  if (!isAuthenticated) {
    return <Navigate to="/login" replace />;
  }

  return children;
};

--------------------------------------------------------------------------------
GATE 6: Follow Request Gate (PRIVATE FOLLOW SYSTEM)
--------------------------------------------------------------------------------
LOCATION: backend/routes/users.js

SIMPLE MEANING:
  You cannot instantly follow someone.
  You SEND a request -> they ACCEPT or DECLINE.

  Routes:
    POST /api/users/:id/follow          -> send / cancel / unfollow
    POST /api/users/:id/accept-follow   -> accept request
    POST /api/users/:id/decline-follow  -> decline request

FLOW (very simple):
  1. A sends follow request to B
     -> A.sentFollowRequests gets B
     -> B.followRequests gets A
  2. B accepts
     -> remove from request lists
     -> B.followers gets A
     -> A.following gets B
  3. Now A can see B's posts in feed/profile

PART 5: SIMPLE FLOW TO EXPLAIN TO LECTURERS
================================================================================

1. User opens website (React frontend on port 3000)
2. Not logged in -> ProtectedRoute sends them to Login
3. User registers/logs in
4. Backend checks data, hashes password (register) or compares (login)
5. Backend returns JWT token
6. Frontend stores token in localStorage (AuthContext)
7. Next API calls include: Authorization: Bearer <token>
8. authMiddleware verifies token (BACKEND GATE)
9. User can create posts, like, comment, search, send follow requests
10. Feed only shows posts from self + followed users (privacy)

PART 6: EMAIL VERIFICATION SYSTEM (NEW FEATURE)
================================================================================

OVERVIEW:
  When a user registers, a 6-digit code is emailed to them.
  They MUST verify before they can log in.
  Code expires in 10 minutes.
  Login is also blocked for unverified accounts.

HOW THE FLOW WORKS:
  1. User fills signup form -> POST /api/auth/register
  2. Backend generates a 6-digit code, saves it in DB, emails it
  3. Frontend switches to a "verify" step (code input screen)
  4. User enters code -> POST /api/auth/verify-email
  5. Backend checks code & expiry -> marks emailVerified = true
  6. Backend issues JWT token -> user is logged in

ALSO: If user tries to LOGIN with unverified email:
  Backend returns 403 + needsVerification:true
  Frontend shows the verify code screen on Login page

PART 7: LIKELY VIVA QUESTIONS + SHORT ANSWERS
================================================================================

Q: What stack did you use?
A: MERN - MongoDB, Express, React, Node.js.

Q: How do you secure private routes?
A: JWT + authMiddleware on backend, ProtectedRoute on frontend.

Q: Where is the auth gate?
A: backend/routes/authMiddleware.js verifies JWT before private APIs run.

Q: How are passwords stored?
A: Hashed with bcrypt. Never stored as plain text.

Q: Is the feed public?
A: No. Only own posts + posts of followed users.

Q: How does follow work?
A: Request-based. Send request -> other user accepts/declines.

Q: Can anyone delete any post?
A: No. Ownership check: only post.author can delete.

Q: Where is login state kept on frontend?
A: AuthContext + JWT in localStorage.

Q: What database?
A: MongoDB Atlas (cloud), accessed with Mongoose models.

Q: What about AI sentiment/stress?
A: Fields exist in Post/Comment models, but analysis is currently disabled/mocked.

Q: How does email verification work?
A: On register, a 6-digit OTP is generated (backend/routes/auth.js Lines 9-11),
   saved to the User document with a 10-min expiry, and emailed via Nodemailer.
   POST /api/auth/verify-email checks the code/expiry, sets emailVerified=true,
   clears the code, then issues a JWT. Login blocks unverified accounts (Line 215).

Q: What sends the email?
A: backend/utils/email.js - uses nodemailer with Gmail SMTP configured in .env
   (EMAIL_USER and EMAIL_PASS environment variables).

Q: What if the code expires?
A: User clicks "Resend code" -> POST /api/auth/resend-code generates a fresh 6-digit
   code with a new 10-minute window. (backend/routes/auth.js Lines 157-186)

Q: Where are the verification fields stored?
A: In the User MongoDB document: emailVerified (Boolean), verificationCode (String),
   verificationCodeExpires (Date). (backend/models/User.js Lines 56-68)
